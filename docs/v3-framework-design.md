# Фреймворк сопровождения нативного Puppeteer PHP

Статус: проектирование; реализованы первоначальный ignore, инвентаризация публичных
классов/членов и проверка их отбора. Генерация PHP и тестов ещё не реализована.
Рабочая ветка — `v3`, источник заготовок и тестов — `native-wip`.

## 0. Что уже сделано

| Часть | Фактическое состояние в v3 |
| --- | --- |
| tools/upstream/public-api.cjs | Читает публичный entry point установленного puppeteer через TypeScript Program/TypeChecker. Собирает экспортируемые классы, публичные/унаследованные члены, static API, явно объявленные публичные конструкторы и имена остальных runtime-экспортов |
| tools/upstream/ignore.cjs | Однократная инициализация ignore, общий selectApi(), валидация исключений и read-only JSON-отчёт |
| upstream/ignore.json | Редактируемые classes/members/exports; единственный источник отбора API |
| tests/Tooling/ignore.test.cjs | Шесть тестов инвентаризации, отбора, расширения API и сохранности ignore |
| Composer | Добавлены upstream-report и test-tooling |
| PHP-клиент | Пока прежняя реализация Rialto; нативная точка входа не подключена |

Проверенный каталог Puppeteer 24.36.1 содержит 38 экспортируемых классов и 575 членов
с учётом наследования. Это инвентаризация объявлений, не количество реализаций или
процент готовности. Текущий отбор сообщает четыре активных класса и семь методов;
эти числа — наблюдение текущего ignore, а не условия, зашитые в инструменты или тесты.

Экстрактор пока выдаёт имена и kind членов. Полных сигнатур, модели связанных типов,
различения overloads в выходных данных, API-diff и сохранённого api.json ещё нет.
Type-only экспорты пока не включаются в результат, getters/setters представлены
как property. Неявные и унаследованные конструкторы потребуют отдельной обработки.

Нет загрузчика upstream-тестов, PhpSynchronizer, TestTracker, Psalm-конфигурации,
нативных unit/parity runners и общей проверки готовности. Существующие test и stan
относятся к старому проекту; успешный test-tooling не означает готовности пилота.
Ниже описана целевая архитектура, если явно не указано обратное.

## 1. Цель и границы ответственности

Сначала построить и проверить инструменты сопровождения порта на API, активном по
текущим ignore-файлам. Затем использовать те же инструменты для переноса остального
публичного API. Расширение охвата выполняется удалением исключений и добавлением
реализаций/тестов, а не новым механизмом обновления для каждого класса.

Три независимых уровня:

1. Детерминированные инструменты получают upstream, извлекают API, синхронизируют
   PHP-объявления, отслеживают тесты внешнего поведения, формируют отчёт.
2. Автоматические проверки анализируют API, PHP-типы и поведение.
3. Разработчик или агент читает изменения и отчёты, правит PHP-реализации, тесты и
   явные соответствия. Инструменты не запускают агента и не переводят тела JS/TS.

Runtime клиента: PHP, Amp/Fibers, WebSocket и CDP. Node.js нужен для инструментов и
эталонного Puppeteer. Браузерные функции остаются JS и исполняются в браузере.
Никаких зависимостей runtime от Rialto или Node.js.

Предмет совместимости — публичный API Puppeteer и его наблюдаемое поведение.
Приватные классы, файлы, алгоритмы и зависимости реализации upstream не
инвентаризируются и не отслеживаются. Их изменение само по себе не создаёт задачи
и не блокирует выпуск PHP-клиента. Архитектуру PHP выбирает разработчик или агент;
он может изучать любые исходники как справочный материал без обязательства
воспроизводить их структуру.

## 2. Архитектура инструментов

| Компонент | Вход | Выход | Разрешённые изменения |
| --- | --- | --- | --- |
| SourceResolver | package.json, lock-файлы | точные исходники пакета и тестового репозитория | кеш upstream, сведения о разрешённых версиях |
| ApiExtractor | TypeScript Program/TypeChecker, точки входа | структурированная модель API | генерируемый API-каталог |
| ApiSelector | API-каталог, ignore | активные объявления и устаревшие исключения | ничего; общий selectApi() уже есть |
| PhpSynchronizer | активный API, правила типов, существующий PHP AST | классы, объявления, заготовки | объявления и выделенные генерируемые аннотации |
| TestTracker | активный API, upstream-тесты, fixtures, карта тестов | новые/изменённые/неперенесённые сценарии активного API | каталог тестов и отчёт |
| Verifier | синхронизированный проект и выбранный охват | диагностика API, Psalm, PHPUnit, parity | только артефакты проверок |
| Reporter | результаты остальных компонентов | JSON и читаемый отчёт | только отчёты |

Компоненты вызываются отдельными командами и общим updater. Никакой скрытой
перегенерации или принятия изменений при запуске тестов.

## 3. Данные и структура проекта

Предлагаемое размещение:

```text
tools/upstream/             инструменты анализа, синхронизации и отчётов
upstream/config.json       ручная конфигурация соответствий и правил типов
upstream/ignore.json       редактируемые исключения публичного API
upstream/lock.json         точные версии пакета, инструментов и ревизия тестов
upstream/api.json          генерируемая структурированная модель API
upstream/tests.json        генерируемый каталог upstream-тестов
src/                       поддерживаемый PHP-клиент
src/Generated/             только полностью генерируемые данные/артефакты
tests/Tooling/             проверки самого фреймворка на небольших fixtures
tests/Unit/                проверки PHP-компонентов
tests/Parity/              парные сценарии PHP/JS и общие данные
.build/upstream/           кеш старых и новых исходников, staging
.build/reports/            диагностика, результаты, логи и traces
```

Из перечисленных служебных файлов сейчас существует только upstream/ignore.json
и его README. config.json, lock.json, api.json и tests.json предстоит реализовать.
Текущее src/ содержит старый клиент, а tests/ — его тесты и новый tests/Tooling.

Будущая конфигурация описывает:

- публичные точки входа; охват определяется отдельным upstream/ignore.json;
- соответствия TS-symbol → PHP FQCN и member → PHP member, включая aliases;
- правила преобразования типов, свойств, getters, callbacks и overloads;
- связи upstream test → PHP test/parity scenario;
- метаданные платформенных требований тестов. Отложенный API задаётся только в ignore,
  второго списка включений/исключений в config нет.

Точные версии хранятся в lock, а не дублируются в PHP-файлах.
API и test-каталоги коммитятся для review; временные результаты — нет.
Схемы всех JSON-файлов версионируются и валидируются.

Отдельного принятия приватных исходников или статуса reviewed нет.
Объём оставшейся работы определяется несоответствием публичному API, заглушками,
неперенесёнными тестами внешнего поведения и результатами проверок.
Результаты проверок привязаны к содержимому PHP, тестов, конфигурации и окружению;
после их изменения старый успешный отчёт не считается актуальным.

## 4. Воспроизводимые входы и охват публичного API

Сейчас проверяется совпадение установленной версии puppeteer/puppeteer-core с
package.json. Исходники не скачиваются инструментом. Корневой package-lock.json
исключён из Git, TypeScript задан диапазоном, поэтому воспроизводимое получение
входов ещё не обеспечено.

Требование к SourceResolver: версия Puppeteer в package.json точная, npm-зависимости
фиксируются коммитящимся lock-файлом сборочных инструментов;
повторный запуск использует закреплённое дерево, а не новое разрешение диапазонов.
Предыдущую и новую целевую версии можно получить воспроизводимо.

Набор upstream-тестов получают отдельно из репозитория на ревизии, соответствующей
пакету. Ревизию и происхождение соответствия фиксируют; произвольный master не
используют. Если соответствие подтвердить не удалось, тестовый источник считается
неразрешённым, а отчёт не заявляет проверку против тестов этой версии.

Инвентаризация строится по публичным экспортам и используемым ими типам параметров,
результатов, событий и callbacks. Типы разрешаются независимо от расположения файла:
объявление во внутреннем каталоге может участвовать во внешнем контракте.
Это разрешение публичных типов, а не обход зависимостей реализации.

Изменения API показываются сравнением структурированных каталогов предыдущей и
целевой версии. Изменения тестов внешнего поведения показываются отдельно.
Приватные изменения при неизменном API не создают структурной диагностики.
Проверки поведения запускаются против целевой версии даже при неизменных сигнатурах.

## 5. Модель API и типы

Использовать TypeScript Program/TypeChecker и разрешение экспортов, а не только
обход файлов по glob или форматирование строк аннотаций. Дорабатывать существующий
tools/upstream/public-api.cjs, сохраняя общий источник каталога для всех инструментов.
Из старого doc-generator.ts можно использовать подходящие части форматирования,
но не его Rialto-преобразования или второй независимый обход API.

Полная модель каталога должна содержать классы, интерфейсы, aliases, enums, функции,
статические члены, конструкторы, свойства, getters/setters, методы и overloads. Учитываются наследование,
callbacks, события, generic-параметры и типы внутри union/collection/Promise.
У публичного символа есть исходный путь, qualified name, kind и ссылки на типы;
у члена — владелец и имя. Номер строки служит диагностике, но не идентификатором.

Разные формы не превращаются автоматически в отдельные PHP-классы: options могут
быть array shapes. Соответствия публичных типов задаются в конфигурации.
Приватные CDP-классы не получают обязательных PHP-аналогов.

Правила типов:

- Promise<T> → Amp\Future с Psalm-типом результата; синхронные методы остаются
  синхронными. Для Promise<void> задаётся явное соответствие завершению без значения.
- TS number не превращается безусловно в PHP float: выбирается допустимое
  int|float либо более точный тип по явному правилу.
- Nullable, optional и undefined различаются; null не назначается автоматически
  значением по умолчанию для всех optional-параметров.
- Generic-типы, shapes и литералы сохраняются в Psalm-аннотациях, даже если нативный
  PHP-тип менее выразителен.
- Браузерная JS-функция и PHP-host callback — разные явно описанные типы.
- Неизвестный тип не теряется в молчаливом mixed. Временный mixed допустим только
  вместе с незакрытой диагностикой; готовность соответствующего API блокируется.
- Overloads без однозначного PHP-представления требуют явного правила. Они не
  схлопываются выбором последнего объявления.

## 6. Правила изменения PHP

Использовать PHP AST с сохранением форматирования и исходных тел. Не загружать
классы через Reflection: на этапе переноса они могут ещё не компилироваться вместе.

| Изменение upstream | Автоматическое действие |
| --- | --- |
| Новый класс | создать заготовку согласно карте соответствий |
| Новый метод | добавить сигнатуру, PHPDoc и явное исключение NotImplemented |
| Новая сигнатура | заменить объявление и генерируемые аннотации, сохранить тело |
| Изменилось только тело JS | никаких структурных изменений; выполняются проверки поведения |
| Удалён метод | сохранить реализацию, отметить obsolete; решение принимает разработчик |
| Переименование/перемещение | показать кандидаты; без однозначного mapping не перепривязывать |
| Конфликт локального объявления | оставить конфликтующую часть и выдать диагностику |

Таблица применяется только к активному API после selectApi(). Исключённые объявления
не создаются и не изменяются генератором. Собственные вспомогательные PHP-классы
и методы не обязаны иметь upstream-соответствие.

Генератор владеет объявлениями сопоставленных публичных членов и выделенными
генерируемыми аннотациями. Тела, ручные комментарии, внутренние методы и бизнес-логика
принадлежат разработчику. Это относится и к конструкторам, свойствам и getters:
изменение типа не разрешает автоматически переписывать initializer или тело.

При переименовании параметра тело не изменяется. Psalm и тесты проверяют последствия;
смысловое переписывание переменных не относится к синхронизации сигнатур.

Патч сначала строится в staging. Проверяются синтаксис, сохранность тел и отсутствие
непредусмотренных правок. Независимые однозначные изменения могут быть опубликованы
единым восстанавливаемым пакетом, а оставшиеся конфликты перечислены в отчёте.
Проверка типов/наследования и поведения выполняется после синхронизации: ошибки в
ещё не адаптированной реализации ожидаемы и не должны приводить к переписыванию тела.
Повторный запуск с теми же входами не меняет файлы. Параллельные updater блокируются.

## 7. Сопровождение тестов

Три категории проверок:

1. Contract: API-каталог сравнивается с реальными PHP-объявлениями, проверяются
   aliases, параметры, типы, static/instance и доступность унаследованных публичных
   членов. Внутреннюю иерархию классов JS копировать не требуется. Дополняет Psalm.
2. PHP unit: транспорт, Future, отмена, ресурсы и компоненты с управляемым окружением.
3. Parity: одинаковые наблюдаемые сценарии выполняются оригинальным JS-клиентом
   и PHP-клиентом в одинаковом браузерном окружении.

Тесты публичного поведения upstream переносятся и связываются с PHP-сценариями.
Unit-тесты приватных JS-абстракций находятся вне охвата и не требуют ни переноса,
ни обоснования отсутствующего PHP-аналога. Собственные PHP unit-тесты проверяют
выбранную PHP-архитектуру независимо от внутреннего устройства JS-клиента.

TestTracker ищет и инвентаризирует тесты внешнего поведения активного API и их
тестовые зависимости. Не нужно переносить каталог всех приватных или исключённых
сценариев как условие готовности пилота. Поиск по имени метода — подсказка, а не
доказательство соответствия: связь теста с API должна быть однозначной либо
подтверждаться явной картой. Неоднозначные кандидаты видны в отчёте.
Fixtures и hooks отслеживаются, чтобы не пропустить изменение самого сценария;
эта связь не распространяется на приватные зависимости клиентской реализации.
ID включает путь, describe/it-иерархию и вариант параметризации. Динамически созданные или
повторяющиеся случаи требуют явного mapping; они не исчезают из отчёта. Для hooks,
fixtures и helpers вначале применяется консервативное отслеживание целых файлов.
Переименование теста считается add/remove до подтверждения соответствия.

Для каждого активного поведения должен быть исполняемый тест. Если подходящего
upstream-теста нет, разработчик/агент добавляет собственный parity-сценарий и
указывает его связь с API; отсутствие теста upstream не является вечной блокировкой.
Общие fixtures и наборы данных переиспользуются. При повторной синхронизации
сохраняются написанные тела PHP-тестов; изменённый upstream-тест создаёт диагностику,
а не автоматически перезаписанные assertions.

Отчёт различает новые, изменённые, удалённые, сопоставленные, исключённые и
неразрешённые тесты. Он не утверждает, что знает, какой тест обнаружит любую ошибку.
При изменении общего транспорта выполняется весь текущий parity-набор.

Автоматически можно создавать PHP-заготовки тестов с markTestIncomplete, но не
переводить assertions и логику. Incomplete, skip и отсутствие соответствия не
считаются доказательством совместимости. Необоснованные пропуски блокируют готовность
выбранного охвата независимо от exit code PHPUnit.

Общие JSON-данные, HTML fixtures, браузерные setup/observation JS используются
обоими исполнителями. Сложные сценарии имеют два небольших поддерживаемых тела.
Универсальный DSL или транспилятор тестов не строится.

JS-эталон выполняется из целевой версии. Его assertions сохраняются: одинаковый
ошибочный результат PHP и JS сам по себе не означает успешный тест. PHP-тесты
также сохраняют ожидаемые свойства сценария; parity добавляет сравнение наблюдений.

Запуски имеют отдельные контексты/профили там, где нужна изоляция, одинаковую версию
браузера и локальные fixtures. Нормализуются только явные нестабильные поля.
Undefined/null, object/array, ошибки и значимый порядок событий не сливаются.
Для конкурентности проверяются причинный порядок и прогресс операций, а не точное
равенство миллисекунд. Таймаут/падение JS или PHP всегда является ошибкой сценария.

При смене версии можно дополнительно сравнить старый JS с новым JS. Эта диагностика
помогает объяснить изменения upstream, но не заменяет сравнение нового JS с PHP.

## 8. Выбор API через ignore, команды и отчёт

Ignore-файлы — единственный механизм выбора API для переноса и проверки совместимости
на всех этапах разработки. Отдельных режимов выбора API нет.
Сейчас используется один файл upstream/ignore.json с секциями classes, members и
exports. Имена точные; wildcard-правил нет. initializedFrom хранит версию начального
заполнения и не определяет текущую версию пакета или состав пилота. Инициализация
однократная; обычный updater никогда не восстанавливает удалённые исключения.
Аргумент --keep существует только у команды init для первоначального заполнения
файла, не сохраняется как второй фильтр и не используется при последующих проверках.

Удаление записи метода включает этот метод. Удаление записи класса включает весь
его публичный API, кроме отдельных записей members. Наследуемые методы учитываются
под именем принимающего класса. Все этапы применяют один и тот же фильтр: создание
PHP-файлов/методов, поиск и создание заготовок тестов, оценка готовности.

Исключённые классы и методы не получают автоматически файлов и тестов. Их определения
могут читаться для разрешения типов активной сигнатуры. Генератор сообщает, какие
типы нужны для этой сигнатуры; отсутствующее PHP-представление необходимо реализовать.
Например, результат Page.goto требует корректного представления HTTPResponse|null.
Разработчик/агент вправе создать нужный PHP-тип как часть реализации активного метода,
оставив HTTPResponse в ignore: переносить все его методы и тесты не требуется.
Ignore ограничивает автоматическую синхронизацию и обязательный API, а не устройство
ручной реализации. Нельзя заменить результат на mixed/null только ради обхода проверки.

Тест активного API может использовать исключённые методы для подготовки/наблюдения.
Эта зависимость показывается в отчёте. При переносе теста можно заменить её общей
fixture, активным API или средствами тестового окружения, сохранив проверяемое
поведение. Например, title наблюдается через evaluate, а браузер для connect
запускает внешний runner. Такой тест не требует неявного включения Page.title или
Puppeteer.launch. Общие fixtures/hooks выбранных тестов сопровождаются вместе с ними.

Новый класс или метод активного класса по умолчанию активен; updater не добавляет
его в ignore. Исключённый класс остаётся исключённым целиком, включая новые методы.
Устаревшие имена исключений требуют исправления. Ignore не удаляет существующие
реализации и не является списком подавления ошибок Psalm/существующих unit-тестов.

Интерфейс Composer:

| Команда | Сейчас | Целевая ответственность |
| --- | --- | --- |
| composer upstream-report | Реализован отчёт выбора API | Объединённый отчёт по API, заготовкам и проверкам |
| composer test-tooling | Реализовано: шесть тестов | Все проверки самого фреймворка |
| composer update-php | Нет | Синхронизация объявлений и тестовых заготовок с учётом ignore |
| composer verify-php | Нет | Read-only проверка актуальности объявлений и API-контракта |
| composer psalm | Нет | Статический анализ нового PHP-клиента |
| composer test-unit | Нет | Unit-тесты новой PHP-инфраструктуры |
| composer test-parity | Нет | Сравнение активного API PHP/JS |
| composer verify-php-release | Нет | Проверка полного публичного API при пустых исключениях |

update-php получает исходники, строит каталоги, применяет структурные изменения и
пишет отчёт. Не запускает агента и не изменяет реализации.
verify-php работает без изменения исходников: проверяет воспроизводимость,
структуру API, заглушки и актуальность артефактов. Проверки можно объединить в
одну CI-команду; каждый этап остаётся доступен отдельно.

Глобальная инвентаризация публичного API остаётся полной: исключённое явно deferred.
Успешная проверка активного API никогда не выдаётся за полный релиз. Финальная
проверка полного клиента требует пустого ignore для заявленного публичного API.

Текущий upstream-report только выводит активные имена и stale-исключения. Он не
проверяет реализации, сигнатуры или тесты. Правила и команды инициализации описаны
в upstream/README.md. Объединённый отчёт ниже — требование к следующей реализации.

Отчёт содержит независимые признаки, а не один неясный статус ready:

- contract: synced / missing / conflict / unsupported / obsolete;
- implementation: stub / present (present не означает корректность);
- tests: unmapped / changed / incomplete / passed / failed / not-run.

Каждая диагностика имеет стабильный code, componentId, symbolId/testId, исходный
и PHP-путь/строку, ожидаемое/фактическое значение и ссылку на diff или лог.
JSON пригоден для агента, текстовый отчёт — для человека. Одинаковые входы дают
одинаковый порядок и содержание структурных диагностик.

Коды завершения: 0 — этап успешен в выбранном охвате; 1 — нужны исправления;
2 — инструмент/окружение не позволили закончить проверку. Для update-php код 0
означает только успешную синхронизацию, а не совместимую реализацию. Report и
release-check отдельно оценивают незавершённые работы.

## 9. Пилот и критерии готовности фреймворка

Пилот должен полностью проходить с текущими ignore-файлами проекта. Его состав —
весь публичный API, который они оставляют активным на момент запуска. Отдельного
фиксированного списка классов, методов или обязательного сценария пилота нет.
После изменения ignore тот же критерий применяется к новому составу активного API.

По этому составу выполняются генерация заготовок, поиск и перенос тестов, реализация
и проверки совместимости. Исключённый API отражается в отчёте, но его реализация
не является условием завершения пилота. Ради успешного прогона нельзя автоматически
добавлять исключения или менять ignore внутри тестов и команд проверки.

Код WebSocket/CDP и сравнительные тесты берутся из native-wip с адаптацией.
Удаление Rialto из новой точки входа и зависимостей выполняется при сборке пилота;
оно не должно уничтожать исходные пользовательские примеры и прототипы.

Для активного API должны проходить проверки публичного контракта, Psalm, unit-тесты
и сравнительные сценарии PHP/JS. Заглушки, отсутствующие или незавершённые обязательные
тесты, неразрешённые типы и расхождения поведения не допускаются. Вспомогательные
проверки конкурентности, ошибок и ресурсов строятся на доступном активном API и
PHP-инфраструктуре, не включают исключённые публичные методы неявно.
У тестов ограниченное время выполнения и диагностические артефакты.

Результат пилота фиксирует использованные ignore-файлы и фактический перечень
активного API. Изменение ignore делает предыдущий результат неактуальным.
Готовность пилота не требует пустого ignore или прохождения проверки полного релиза.

Сам фреймворк проверяется на маленьком версионированном TS/PHP fixture-проекте:

1. Новый активный класс/метод создаёт соответствующую заготовку; связанный тип
   разрешается по правилам типов и ignore. Исключённый API автоматически не создаётся.
2. Изменение параметров и результата обновляет объявление без изменения тела и
   ручных комментариев; несовместимость тела обнаруживается проверками.
3. Изменение приватного алгоритма или helper при прежнем API не меняет PHP-объявления
   и не создаёт требования переноса; проверки поведения всё равно выполняются.
4. Новые, изменённые, удалённые тесты и изменение fixture обнаруживаются.
5. Наследование, Promise, options shape и неоднозначный overload обрабатываются
   по правилам либо дают явную ошибку; неизвестное не скрывается.
6. Повторная синхронизация не меняет байты файлов; конфликт не уничтожает код.
7. Намеренная ошибка в PHP меняет parity на failed с понятной диагностикой.
8. Нереализованный публичный метод, incomplete-тест и несоответствие API блокируют
   готовность активного API; исключённые части не скрываются глобально.
9. Удаление исключения класса/метода включает его создание и поиск тестов без
   дополнительного allowlist или специальной ветки инструмента для его имени.
10. Старый положительный отчёт не принимается после изменения входных файлов.

На данный момент реализованы проверки отбора и сохранности ignore; весь этот
перечень ещё не выполнен. Изменения ignore для fixture-тестов делаются в изолированных
данных теста, не в рабочем ignore проекта.

После синтетических проверок выполняется тот же процесс на реальном пилоте.
Покрытие всех видов TypeScript на первом этапе не требуется: неподдержанные формы
должны честно диагностироваться и расширяться общими правилами при полном переносе.

## 10. Порядок реализации и дальнейшая работа агентов

1. Расширить текущий API-каталог сигнатурами и связанными типами; сохранить действующие
   ignore и selectApi(). Зафиксировать схемы каталогов и fixture v1/v2.
2. Добавить воспроизводимое получение пакетов и соответствующих upstream-тестов;
   определить lock и правила публичных JS → PHP типов.
3. Реализовать PHP AST-синхронизацию и contract-проверку на fixture v1/v2.
4. Реализовать TestTracker, Psalm/PHPUnit/parity runner и объединённый отчёт.
5. Подключить транспорт и публичный API, активный по текущим ignore, перенести тесты
   и пройти полный цикл на настоящем Puppeteer. Использовать из native-wip подходящий
   код, не переносить автоматически старый компилятор и весь runtime эмуляции JS.
   Исправить общие недостатки инструментов.
6. После прохождения критериев удалять классы/методы из ignore и переносить их.

Для полного переноса отчёт служит входом задач человеку или субагентам.
Задача содержит публичный контракт, разрешённые PHP-файлы, diff API и тестов,
результаты проверок. Внутренние зависимости PHP определяются выбранной реализацией.
Параллельно выполняются независимые компоненты; общий файл имеет одного владельца.
Изменение общих правил типов, транспорта и инструментов выделяется в отдельную
задачу, а не дублируется в каждой реализации. Сам updater таких задач не запускает.

Фреймворк готов к масштабированию после прохождения критериев пилота и его
собственных fixture-тестов. Это готовность процесса сопровождения, а не заявление
о завершении полного Puppeteer-клиента.
