# QuickJS / native PHP / Rialto: результаты прототипа

Замер на этой машине: Apple M1 Max, macOS arm64, PHP 8.5.7 NTS,
Chrome 152.0.7977.83, Puppeteer 24.36.1. Для QuickJS загружено расширение из
форка с `runJobs()`/`hasPendingJobs()` и поддержкой последовательных входов
из PHP Fibers. Все клиенты выполняли одинаковые проверки результатов.

## Результаты

Медианы пяти отдельных запусков каждого клиента. Для p50/p95 указана медиана
соответствующего показателя пяти прогонов, а не объединённая выборка.

| Измерение | Rialto (PHP + Node) | Native PHP | QuickJS |
|---|---:|---:|---:|
| Подключение + создание страницы + первая навигация, мс | 488.86 | 239.10 | 329.12 |
| 1000 последовательных evaluate, мс | 413.02 | 331.68 | 579.70 |
| Медианная задержка evaluate, мс | 0.38 | 0.31 | 0.53 |
| p95 задержки evaluate, мс | 0.62 | 0.47 | 0.78 |
| 100 возвратов строки 64 КиБ, мс | 114.60 | 103.78 | 2552.03 |
| 20 операций с задержкой 25 мс, мс | 545.30 | 29.64 | 32.97 |
| 20 навигаций + title, мс | 504.02 | 497.84 | 506.11 |
| CPU всего клиентского процесса/дерева за запуск, мс | 830.00 | 360.00 | 3120.00 |
| Пиковая RSS клиентского дерева, МиБ (семплирование) | 123.55 | 38.14 | 73.47 |

## Вывод

В этом прототипе QuickJS не ускоряет последовательные вызовы относительно Rialto
или native PHP. Он сохраняет оригинальную логику Puppeteer и позволяет обойтись
без Node.js в клиенте, использует меньше RSS, чем PHP + Node.js, и выполняет
конкурентные ожидания браузера без их сериализации. Native PHP остаётся самым
экономным из проверенных вариантов, но его API реализован лишь частично.

Наиболее дорогой для QuickJS сценарий — 100 возвратов строк по 64 КиБ.
Архитектура текущего моста передаёт CDP-строки и результаты через MessagePack,
а прототип дополнительно кодирует сообщения в JSON. Это кандидат для отдельного
профилирования и оптимизации; данный замер не доказывает, сколько времени
занимает каждый конкретный слой. Расход CPU в итоговой строке сильно зависит
от включённого сценария с большими строками.

## Методика и ограничения

- Каждый запуск: отдельный PHP-процесс и свежий Chrome с новым профилем.
  Chrome запускает внешний Node-runner; он не является частью клиента QuickJS/native.
- В режиме Rialto учитывается PHP и дочерний Node.js. Chrome, HTTP fixture,
  runner и процесс измерителя исключены из CPU/RSS клиента во всех вариантах.
- Используется `php -n`: Xdebug отключён; QuickJS загружается только в его режиме.
- Перед измерением последовательных вызовов — 50 прогревочных evaluate.
- Порядок клиентов циклически меняется между повторами. Прогоны выполняются
  последовательно. Это локальный микробенчмарк, не прогноз нагрузки реального сайта.
- В CPU-строке показана сумма user + system из `/usr/bin/time -l` для завершённой
  PHP-команды и её дочерних процессов: сюда входят запуск, подготовка, прогрев,
  все четыре сценария и завершение. Это CPU-время, не процент загрузки процессора.
- RSS — максимальная наблюдённая сумма RSS PHP и его живых потомков, с интервалом
  25 мс. Короткие пики могут быть пропущены; общие страницы памяти процессов могут
  учитываться несколько раз. `memory_get_peak_usage()` PHP не охватывает QuickJS
  и Node, поэтому для сравнения памяти используется RSS.
- Сырые результаты также содержат приблизительный CPU по семплам `ps` и CPU PHP
  для отдельных фаз. Последний не включает Node и не подходит для прямого
  сравнения CPU Rialto с остальными клиентами.
- На фоновой вкладке `click()` с ожиданием IntersectionObserver зависал и у
  оригинального Node Puppeteer, и у QuickJS. Smoke-тест активирует вкладку перед
  кликом. Сценарий click не входит в микробенчмарк.
- Полный Puppeteer API, Firefox/BiDi, запуск/скачивание браузера из PHP,
  puppeteer-extra/Node-плагины и стабильность под длительной нагрузкой не проверены.

Данные: [benchmark.json](benchmark.json). Повторный запуск из корня проекта:

```sh
BENCH_TRIALS=5 BENCH_ITERATIONS=1000 node prototypes/quickjs/benchmark.cjs
```
